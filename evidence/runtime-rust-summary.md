# Rust Kata / capped-storage qualification

The dedicated `openshell-kata-enforcement` Lima node ran the official Kata 4.3.1 Rust shim at `/opt/kata/runtime-rs/bin/containerd-shim-kata-v2` with Dragonball. No Go Kata compatibility runtime was used for these tests. Docker, containerd, nerdctl, and Lima remain external projects with their own implementation languages.

The configuration uses `virtio-blk-mmio` for the VM and container block devices and `shared_fs = "none"`. A guest reported kernel 6.18.56. Its writable `/` was `/dev/vdb` on a devmapper snapshot with exactly 2,147,483,648 bytes. The agent image `/dev/vda` was 268,435,456 bytes and remained read-only. Guest root attempted to clear its read-only flag and write back an unchanged byte; the write failed with `Operation not permitted` and the device still reported read-only. The guest mount table contained no 9p or virtiofs mounts. The generated OCI spec had no host bind mounts or host device entries.

Docker 29.9.2 built an image from scratch, ran it, and ran a Compose service inside this guest. `runtime-rust-docker-proof.log` records `RUST_KATA_DOCKER_RUN_OK`, `RUST_KATA_COMPOSE_OK`, and `RUST_KATA_PROOF_COMPLETE`. This was an offline workload with no external network; network-policy qualification belongs to the integration suite.

`ctr containers info ID` exposes the exact `SnapshotKey` and `Snapshotter`. `ctr snapshots --snapshotter devmapper mounts /not-mounted KEY` prints the backing-device mount command without executing it. `blockdev --getsize64 DEVICE` provided the host-side cap measurement. Do not use `--temp`, which would mount the filesystem.

The Rust shim process, its `vmm_master` thread, and its single `db_vcpu0` thread were all in `/openshell-kata/proof`. OCI resource fields sized the guest but left host `cpu.max` and `memory.max` unlimited. Host control must therefore explicitly install the cgroup limits. Applying `cpu.max = 100000 100000`, `memory.max = 2147483648`, `memory.swap.max = 0`, and `memory.oom.group = 1` constrained the complete Rust process. A later guest file-fill test reached the memory cap and the host kernel killed the whole VM cgroup. That test is evidence of memory enforcement, not a successful filesystem ENOSPC test.

The thin pool initially used `skip_block_zeroing`; that unsafe setting was removed after all I/O was quiescent and before tenant admission. Its live table now enables default block zeroing and `error_if_no_space`. `setup-devmapper.sh` creates the safe form and rejects an existing pool that still disables zeroing. A temporary 2 GiB thin-device canary verified zeroes after a partial-block write and received `No space left on device`, with zero bytes written, at byte offset 2,147,483,648. The canary and its thin ID were removed.

The final image is `openshell-kata-enforced:local`, manifest `sha256:783b0ad9648e44b27e5324a83304ab7a04c224efc91085918450b8e7a697fac6`, index `sha256:3b3c94dac54dd737199bf6cbe9b9083dfd23708fa886b6252167a3e7d7494a53`. It includes the current guest initialization code, curl, iproute2, bind-tools, netcat-openbsd, GNU coreutils, and OpenSSH. Trusted image assembly uses a nonprivileged runc container inside the dedicated node; user workloads used Rust Kata.

Containerd transfer unpacking required explicit `unpack_config` entries for the devmapper and overlayfs snapshotters. This is persisted in `setup-devmapper.sh`; [containerd's transfer configuration implementation](https://github.com/containerd/containerd/blob/v2.3.3/plugins/transfer/plugin.go) defines those fields. The kernel documents default thin-pool zeroing and the [meaning of `skip_block_zeroing`](https://docs.kernel.org/admin-guide/device-mapper/thin-provisioning.html).

All task-owned build seeds, proof containers, snapshots, and the extra thin-device canary were removed after component qualification. The prepared image was then used by the combined CLI and boundary suite recorded in `enforcement-qualification.json`; its dedicated node was removed after final evidence capture.
